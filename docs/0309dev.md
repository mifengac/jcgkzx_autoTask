# 0309 开发清单: 监控脚本平台重设计

## 1. 目标

把当前“脚本 + Docker + crontab + 环境变量”的离散运行方式，重构为一个可通过 Web 前端管理的任务平台，满足以下核心目标：

1. 前端可上传脚本。
2. 前端可配置发送规则，不再把接收人逻辑写死在脚本里。
3. 前端可配置执行频率，当前仅支持“分钟”和“小时”两个单位。
4. 支持固定联系人、按单位编码匹配联系人、按单位编码向上级单位递归匹配联系人。
5. 支持前端配置短信模板。
6. 脚本执行、命中规则、短信发送、失败重试都有日志和可追踪记录。

本轮确认后的新库模式名建议定为：`jcgkzx_autotask`

## 4. 重设计原则

1. 脚本负责“取数”和“输出标准化结果”，不负责发短信。
2. 规则引擎负责“根据结果行生成接收人列表”。
3. 调度器负责“按频率触发任务”。
4. 发送服务负责“短信去重、发送、重试、回执记录”。
5. 前端只操作元数据、规则、频率、启停和测试，不直接碰服务器命令。
6. 联系人主数据进入新模式后统一使用新表，不再直接读取旧表。

## 6. 核心设计: 脚本标准接口

“支持前端上传脚本”这件事，真正的关键不是上传，而是定义标准接口。

建议脚本统一约定：

1. 输入：
   - 任务参数 JSON
   - 本次运行时间窗口
   - 数据库连接配置引用
2. 输出：
   - 标准 JSON 数组
   - 每一行必须是字典
   - 字段名稳定
3. 必选输出字段：
   - `event_id` 或可唯一识别业务行的字段
   - `event_time`
   - `message_vars`
4. 可选输出字段：
   - `sspcsdm`
   - `dwdm`
   - `xqdm`
   - `case_no`
   - 其他业务字段

建议统一脚本入口：

```python
def run(context: dict) -> list[dict]:
    ...
```

或者命令行模式输出 JSON：

```bash
python script.py --context-json /tmp/context.json
```

### 6.1 更好的建议

不要允许前端直接上传“任意 Python 并立即执行”。

更稳妥的方案：

1. 上传 zip 包。
2. zip 内必须包含 `manifest.json`。
3. `manifest.json` 声明：
   - 脚本名称
   - 入口文件
   - 入口函数
   - 依赖需求
   - 输出字段定义
   - 默认参数
4. 后端先校验，再入库，再发布。

否则后续会遇到安全、依赖污染、输出不稳定、升级回滚困难的问题。

## 7. 核心设计: 频率模型

满足你当前要求即可，先不做复杂 cron。

建议前端配置字段：

- `interval_value`
- `interval_unit`

支持值：

- `interval_unit = minute`
- `interval_unit = hour`

示例：

- 20 分钟: `20 + minute`
- 3 小时: `3 + hour`

后端统一换算为秒或 APScheduler interval。

同时增加：

- `enabled`
- `start_at`
- `end_at`
- `timezone`
- `max_concurrency`
- `misfire_policy`

## 8. 核心设计: 发送规则模型

建议把一条任务拆成：

- 脚本定义
- 调度配置
- 发送模板
- 多条发送规则

每条规则独立启停、独立优先级、独立作用范围。

### 8.1 规则类型一: 固定人员

用途：

- 手工配置固定手机号
- 用于全局兜底
- 用于领导、值班员、测试接收人

配置项：

- 规则类型: `fixed_receivers`
- 联系人列表
- 是否去重
- 是否允许和其他规则叠加

### 8.2 规则类型二: 直接匹配

你的需求已经确认：

- 默认优先匹配联系人表的 `sspcsdm`
- 但平台必须允许切换目标字段
- 平台也必须允许切换脚本输出里的源字段

建议前端配置项：

- 规则类型: `field_match`
- 源字段名: 例如 `dwdm` / `sspcsdm`
- 联系人表: `jcgkzx_autotask.org_contact`
- 目标字段名: 例如 `sspcsdm` / `xqdm`
- 联系电话来源: `jcgkzx_autotask.org_contact_phone.mobile`
- 附加过滤条件:
  - `rwzt = xxx`
  - `status = active`
  - `mobile is not null`

本轮默认值建议：

- 默认目标字段: `sspcsdm`
- 允许切换目标字段: `xqdm` / `sspcsdm`
- 允许切换源字段: `dwdm` / `sspcsdm` / 其他脚本标准输出字段

执行逻辑：

1. 读取结果行中的源字段值。
2. 去联系人表查目标字段相等的记录。
3. 关联手机号子表。
4. 合并去重。

### 8.3 规则类型三: 匹配当前单位及上级单位

这是本次最关键的新增规则。

建议规则类型命名为：`field_match_with_ancestors`

前端配置项：

- 源字段名: 例如 `dwdm`
- 目标字段名: 默认 `sspcsdm`
- 层级模式: `city_county_station`
- 是否包含本级: `true`
- 是否包含县级: `true`
- 是否包含市级: `true`
- 联系电话来源: `org_contact_phone.mobile`
- 附加过滤条件: 例如 `rwzt = xxx`

#### 8.3.1 编码规则

按你给的例子，12 位单位编码可抽象为：

- 市级: `445300000000`
- 县级/区级: `445302000000`
- 派出所级: `445302180000`

建议平台内统一提供编码归一函数：

```text
输入: 445302180000
本级: 445302180000
县级: 445302000000
市级: 445300000000
```

算法建议：

1. 取前 6 位 + `000000` 得县级
2. 取前 4 位 + `00000000` 得市级
3. 本级保留原值

#### 8.3.2 示例

当脚本结果中的 `dwdm = 445302180000` 时，应查联系人表中的：

- `445302180000`
- `445302000000`
- `445300000000`

命中的所有手机号合并去重后发送。

## 12. 推荐执行流程

1. 调度器触发任务。
2. 执行器加载脚本版本和运行参数。
3. 脚本返回标准化结果列表。
4. 系统逐行执行规则引擎。
5. 规则引擎产出手机号集合。
6. 模板引擎生成短信正文。
7. 防重逻辑判断是否应发送。
8. 调用短信网关发送。
9. 保存执行记录、命中记录、发送记录。

## 13. 防重与幂等建议

必须做，否则新平台上线后很容易重复发短信。

建议至少支持：

1. 按 `task_id + event_key + mobile + dedup_window` 防重。
2. 同一运行批次内去重。
3. 同一规则命中的多个手机号合并去重。
4. 固定人员和单位匹配结果交叉去重。

## 14. 权限与安全建议

这部分必须提前设计，不然后面返工会很大。

1. 脚本上传只允许管理员。
2. 脚本执行环境必须隔离。
3. 禁止脚本直接访问宿主机敏感目录。
4. 数据库和短信网关账号不要暴露在前端。
5. 前端只保存“配置引用”，敏感密钥由后端保管。
6. 记录每次规则变更、脚本发布、任务启停的审计日志。

## 16. 建议优先级

建议不要一上来就做“任意脚本上传 + 任意依赖安装 + 任意运行”。

更稳妥的优先级是：

1. 先把现有 5 个脚本接入统一平台。
2. 先支持平台内置脚本版本管理。
3. 再开放上传新脚本。

原因：

1. 这样可以先验证规则引擎和调度是否可用。
2. 可以避免一开始就处理任意代码执行带来的安全问题。
3. 可以用现有业务脚本做回归基准。

## 17. 已确认决策

1. 规则 2/3 默认匹配联系人表字段 `sspcsdm`。
2. 源字段名可配置，目标字段名也可配置。
3. 短信内容模板由前端管理。
4. 联系人主数据迁移到新模式，不再直接使用 `ywdata.b_dxpt_mdjfyj`。
5. 新联系人模型要同时保留 `xqdm` 和 `sspcsdm`，并增加层级字段，方便做本级、县级、市级递归匹配。
6. 为兼容旧逻辑，在新模式中额外提供兼容视图 `jcgkzx_autotask.b_dxpt_mdjfyj`，但底层真实表以 `org_contact` / `org_contact_phone` 为准。

## 18. 我认为更好的建议

1. 不要把“上传脚本”和“配置发送规则”耦合成一个页面，应该拆成脚本管理和任务编排两个层次。
2. 不要让脚本直接发送短信，统一由平台发，后续才能做重试、审计和回放。
3. 不要继续依赖 `crontab`，平台内部要有自己的调度器。
4. 规则里要允许选择“是否向上包含本级、县级、市级”，不要只写死 3 层。
5. 每条规则都要有“试算”按钮，输入一行样本数据就能看到最终手机号。
6. 每次执行都保留“原始结果 + 命中规则 + 实际发送对象”，否则后面难排错。
7. 联系人表要拆成主表和手机号子表，不要继续把多个号码挤在一个 `lxdh` 文本字段里。
8. 为了平滑替换旧脚本，可以在新模式保留同名兼容视图，而不是继续保留旧结构做主表。

## 19. 最小可行版本 MVP

如果要快速落地，建议 MVP 范围如下：

1. 只接入现有脚本，不开放任意第三方上传。
2. 前端先支持任务管理、频率配置、规则配置、模板配置、执行日志。
3. 先实现 3 类规则：
   - 固定人员
   - 直接匹配
   - 向上级匹配
4. 先复用现有短信发送通道。
5. 跑通后再做脚本上传、版本管理、回滚。

这样能更快替换当前生产方式，风险也更低。
