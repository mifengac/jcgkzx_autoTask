# data_scraper_multi.py 接入平台说明

## 1. 文档目的

本文档说明如何把 [data_scraper_multi.py](C:/Users/So/Desktop/doc/02/jcgkzx_autoTask/data_scraper_multi.py) 接入到新建的平台中。

这个脚本和短信预警类脚本不同：

- 它的目标不是发短信
- 它的目标是定时从一个系统抓取数据
- 再把数据写入另一个系统的数据表

因此，它在平台中的定位应该是：

- 一个“定时导数任务”
- 不是“短信任务”

## 2. 先理解这个脚本现在在做什么

`data_scraper_multi.py` 当前业务逻辑可以概括为：

1. 登录源系统，获取 Cookie
2. 按配置好的多个请求参数并发抓取数据
3. 解析接口响应
4. 按唯一键去重
5. 写入人大金仓目标表
6. 全部任务执行完成后结束

从代码看，它的核心特征是：

- 支持多任务配置 `CONFIG["tasks"]`
- 支持并发请求
- 支持 `append` / `replace`
- 支持目标表自动建表和补字段
- 使用 `unique_key` 做增量更新

这说明它本质上是一个“数据同步脚本”，不是一个“事件告警脚本”。

## 3. 它接入新平台时的正确定位

新平台最初是围绕“脚本结果 -> 规则匹配 -> 短信发送”设计的。

但 `data_scraper_multi.py` 不需要后半段：

- 不需要短信模板
- 不需要发送规则
- 不需要短信发送日志

它真正需要的是：

- 统一调度
- 统一参数配置
- 统一运行记录
- 统一失败排查

所以接入时，应该把它作为一种特殊任务类型来理解：

- `data_sync` 或 “导数任务”

虽然当前平台代码里没有单独的任务类型字段，但业务上应该按这个思路使用。

## 4. 不建议直接上传原始 data_scraper_multi.py

原因很简单：

当前平台约定脚本入口是：

```python
def run(context: dict) -> list[dict]:
    ...
```

而 [data_scraper_multi.py](C:/Users/So/Desktop/doc/02/jcgkzx_autoTask/data_scraper_multi.py) 当前是：

- 以 `main()` 作为入口
- 自己直接登录、抓取、入库
- 不返回标准结果列表

也就是说，它现在是“自执行脚本”，不是“平台插件脚本”。

如果直接上传原脚本，会有两个问题：

1. 平台很难从返回值判断这次运行到底做了什么
2. 平台无法把“抓取了多少条、写入了多少条、哪个子任务失败了”记录得足够清楚

因此，推荐做法不是直接上传原脚本，而是加一层适配。

## 5. 推荐接入方式

推荐做法：

1. 保留 `data_scraper_multi.py` 里的抓取和入库逻辑
2. 新建一个平台入口脚本，例如 `multi_runner.py`
3. 由 `multi_runner.py` 调用 `data_scraper_multi.py` 内部函数
4. 由 `multi_runner.py` 返回标准化结果列表给平台

也就是说：

- `data_scraper_multi.py` 继续负责“怎么抓、怎么写库”
- `multi_runner.py` 负责“怎么适配平台接口”

## 6. 推荐的 ZIP 包结构

建议上传的 ZIP 包结构如下：

```text
multi_import_task.zip
├── manifest.json
├── multi_runner.py
└── data_scraper_multi.py
```

`manifest.json` 示例：

```json
{
  "entry_file": "multi_runner.py",
  "entry_func": "run",
  "script_type": "python_zip"
}
```

## 7. 推荐的适配思路

适配脚本 `multi_runner.py` 的职责应该是：

1. 从平台传入的 `context["runtime_config"]` 读取参数
2. 调用 `data_scraper_multi.py` 中已有的函数
3. 对每个子任务产出一条“执行摘要”
4. 把这些摘要以 `list[dict]` 返回给平台

推荐返回格式示例：

```python
[
  {
    "event_id": "multi_duty_schedule_20260310_081500",
    "task_name": "duty_schedule",
    "target_table": "ywdata.zq_kshddpt_zxzgl",
    "mode": "append",
    "status": "success",
    "fetched_response_count": 10,
    "parsed_record_count": 325,
    "written_record_count": 325,
    "message_text": "导数任务成功: duty_schedule, 写入 325 条"
  }
]
```

这里的 `message_text` 不是为了发短信，而是为了让平台运行记录里能直接看到摘要。

## 8. 这个任务在平台里怎么配置

### 8.1 上传脚本

在“上传脚本”模块中上传上面的 ZIP 包。

平台只认：

- `manifest.json`
- 入口文件
- 入口函数

### 8.2 短信模板

这个任务不需要短信模板。

建议：

- 不配置模板

因为导数任务不是通知任务，短信模板对它没有意义。

### 8.3 任务与频率

这是它最重要的配置模块。

要配置的核心内容是：

- 任务名称，例如“值班表跨天数据同步”
- 频率，例如 `30 + minute`
- 运行参数 `runtime_config`

建议把原脚本中依赖环境变量的内容，尽量迁到 `runtime_config` 中。

例如：

```json
{
  "multi_login_url": "http://68.253.2.107/zhksh/login",
  "multi_login_username": "xxx",
  "multi_login_password": "xxx",
  "multi_api_url_duty": "http://68.253.2.107/zhksh/dutySchedule/crossDayList",
  "multi_db_host": "10.45.100.148",
  "multi_db_port": 54321,
  "multi_db_name": "yfywk",
  "multi_db_user": "xxx",
  "multi_db_password": "xxx",
  "multi_begin_days_ago": 9,
  "multi_end_days_ago": 0,
  "multi_mode": "append",
  "multi_max_workers": 31,
  "multi_request_timeout": 180
}
```

这样以后改频率、改接口地址、改写库方式，都不需要改 Python 文件。

### 8.4 发送规则

这个任务不需要发送规则。

建议：

- 不配置任何规则

这样平台在执行后：

- 会保留运行记录
- 但不会进入短信发送环节

从当前平台逻辑看，不配规则时结果会进入“无接收人，不发送”的分支，这是符合导数任务预期的。

### 8.5 联系人与运行记录

这个任务不需要联系人匹配。

它真正要看的，是“运行记录”。

对这个脚本来说，运行记录比联系人更重要。

## 9. 平台里如何监测这个任务

这个任务的监测重点不是“短信发给谁”，而是“导数是否正常”。

建议重点看 4 类指标。

### 9.1 看任务有没有按时运行

先看：

- 任务是否启用
- 调度频率是否正确
- 最近一次运行时间是否符合预期

如果设定是每 30 分钟一次，就要看最近运行是否持续出现。

如果长时间没有新运行记录，先查：

- 任务是否被停用
- 调度器是否启动
- 数据库是否可连

### 9.2 看运行状态是否成功

重点看 `task_run.status`。

建议关注：

- `completed`
- `failed`
- `completed_dry_run`

对生产导数任务来说，正常应该主要看到 `completed`。

如果经常出现 `failed`，说明：

- 登录失败
- 源接口失败
- 目标库连接失败
- 写库 SQL 失败

### 9.3 看每次运行处理了多少数据

对于导数任务，最重要的不是“命中了几条规则”，而是：

- 抓到了多少响应
- 解析出了多少记录
- 实际写入了多少记录

因此推荐适配脚本把这些值写进返回结果。

这样前端就能通过运行详情看到：

- 这次是不是空跑
- 是源系统没有数据，还是脚本失败
- 是抓到了数据但没写进去，还是根本没抓到

### 9.4 看目标表是否真的有更新

平台运行成功不等于业务成功。

还要看目标表实际是否更新。

以当前脚本中的任务为例，应关注目标表：

- `ywdata.zq_kshddpt_zxzgl`

建议在日常监测时同时看：

1. 平台运行记录是否成功
2. 目标表最近更新时间是否变化
3. 目标表记录数是否有合理增长或更新

## 10. 推荐的监测口径

这个脚本接入平台后，建议把“监测”分成三层。

### 第一层：平台是否调度成功

看平台任务是否按时执行。

判断标准：

- 最近一条运行记录时间正常
- 任务状态不是失败

### 第二层：脚本是否执行成功

看脚本本身有没有完成登录、抓取、解析、写库。

判断标准：

- 运行状态是 `completed`
- 结果摘要中没有错误信息

### 第三层：业务结果是否落库成功

看目标表数据是否真的变化。

判断标准：

- 目标表记录数增加或更新
- 抽查部分数据正确

只有这三层都成立，才能认为“导数任务正常”。

## 11. 推荐增加的返回摘要字段

为了让这个脚本更适合平台监测，建议适配脚本至少返回这些字段：

- `event_id`
- `task_name`
- `target_table`
- `mode`
- `status`
- `fetched_response_count`
- `parsed_record_count`
- `written_record_count`
- `error_message`
- `start_time`
- `end_time`

这样平台虽然不发短信，但仍然能把每次执行情况展示清楚。

## 12. 推荐的人工巡检方法

如果是业务管理员每天巡检，建议看下面几项：

1. 任务列表中该任务是否处于启用状态
2. 最近一次运行是否成功
3. 最近几次运行的结果数是否明显异常
4. 目标表是否有最近更新时间
5. 源系统接口是否可访问

如果是技术人员排障，建议按下面顺序查：

1. 查平台 `task_run`
2. 查平台 `task_run_result`
3. 查脚本日志摘要
4. 查目标表
5. 查源接口返回

## 13. 接入这个脚本时的注意事项

### 13.1 不要把它当成短信任务

这个脚本不需要：

- 模板
- 规则
- 联系人
- 短信发送

如果强行按短信任务方式使用，会让业务含义变乱。

### 13.2 不要只看平台成功，要看目标表

因为这个任务最终目标是“把数据导入目标系统”。

所以平台成功只是第一步，目标表成功更新才是最终结果。

### 13.3 不建议继续完全依赖环境变量

原脚本当前大量使用：

- `MULTI_*`
- `KINGBASE_*`
- `LOGIN_*`

建议接入平台后，逐步迁移到任务的 `runtime_config`。

这样以后平台才能真正做到：

- 前端改参数
- 不改代码
- 不重打包

### 13.4 最好把“每个子任务”的结果独立返回

因为 `data_scraper_multi.py` 支持多任务配置。

如果未来它不止一个 `tasks[]` 项，最好的做法是：

- 一个子任务返回一条摘要

这样平台上能直接看到是哪个子任务失败，而不是整批一起模糊失败。

## 14. 推荐的落地步骤

建议按下面步骤接入：

1. 先把 `data_scraper_multi.py` 保留为底层能力脚本
2. 新建 `multi_runner.py` 做平台适配入口
3. 让 `multi_runner.py` 返回标准结果列表
4. 打包 ZIP 并上传到平台
5. 创建“导数任务”，只配置频率和运行参数
6. 不配置短信模板，不配置发送规则
7. 先手动执行一次
8. 确认目标表写入正常后，再启用定时调度

## 15. 一句话理解这个任务怎么接入

`data_scraper_multi.py` 接入新平台时，不是作为“告警脚本”使用，而是作为“定时数据同步脚本”使用。

平台对它最重要的价值不是发短信，而是：

- 定时调度
- 参数集中管理
- 执行结果留痕
- 失败可追踪

如果要把这类任务长期纳入平台，后续最好在平台中正式增加一种任务语义：

- 短信预警任务
- 数据同步任务

这样业务模型会更清晰。
